## 1. サービス概要

Norutokiは、月に数回利用する「いつものバス移動」を登録しておくことで、現在時刻から次に利用できる便をすぐ確認できる、自分専用の交通情報アプリです。

「行き方は分かっているが、バス停名や時刻までは覚えていない」人が、利用するたびに同じ情報を検索・入力する手間をなくし、「いつもの移動」を検索せず確認できる状態を目指します。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

私は普段、月に数回ほど同じバスを利用します。

利用するバス停の場所や目的地までの行き方はなんとなく分かっているのですが、毎日利用するわけではないため、バス停の正式名称や路線名、出発時刻までは覚えていません。

そのため、バスに乗るたびにバス停の名前を調べたり、バス会社のWebサイトを開いて該当するバス停や方面を探したりして、時刻表を確認しています。

特にバス会社の時刻表は、一日分の時刻が一覧で表示されていることが多く、「今から乗れる次のバスは何時なのか」を確認したいだけなのに、現在時刻と照らし合わせながら探す必要があります。

また、行きのバスだけでなく、外出先から帰るときにも「帰りのバスは次に何時に来るのか」を改めて調べることがあります。

この作業を繰り返す中で、「いつも利用する移動なのだから、行きも帰りも次に乗れるバスの時刻だけすぐ確認できたら便利なのに」と感じたことが、このサービスを考えたきっかけです。

### 2-2. なぜそれが「気になった」のか

私は、すでに分かっている情報を毎回検索し直したり、必要な情報を探すために何度も操作したりすることに煩わしさを感じます。

バスに乗るときも、知りたいのは「どのバスに乗ればいいか」ではなく、「次のバスが何時に来るか」という情報だけです。

それにもかかわらず、毎回バス会社のWebサイトを開いて時刻表までたどり着き、その中から現在時刻以降の便を探す必要があります。

そこで、普段利用する交通情報をあらかじめ登録しておき、必要なときにアプリを開くだけで次の便を確認できれば、日常の小さな手間を減らせるのではないかと考えました。

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

月に数回バスを利用する際、普段利用するバス停の場所や目的地までの行き方はなんとなく分かっていますが、バス停の名前や路線名、時刻までは覚えていません。

そのため、バスを利用するたびにバス停の名前を調べたり、バス会社のWebサイトから該当するバス停や方面を探したりして、時刻表を確認する必要があります。

また、バス会社のWebサイトでは多くの情報が掲載されており、「いつもの場所から次に乗れるバスが何時なのか」を知りたいだけでも、必要な情報にたどり着くまでに複数の確認が必要です。

### 3-2. 本当に解決したい課題は何か

**なぜ①：なぜバスに乗るたびに調べる必要があるのか？**

月に数回程度しか利用しないため、バス停の場所や目的地までの行き方はなんとなく覚えていても、バス停の名前や路線名、時刻までは覚えていないからです。

**なぜ②：なぜ毎回調べることが面倒なのか？**

利用する場所や目的地は毎回ほぼ同じなのに、バス停の名前や路線、時刻表などをその都度調べ直す必要があるからです。

**なぜ③：なぜその手間をなくしたいのか？**

本当に知りたいのは「いつもの場所から次のバスが何時に来るか」という情報だけなのに、そのために毎回同じ検索や入力、確認を繰り返すことに煩わしさを感じるからです。

実際に、調べること自体を面倒に感じ、「このくらいの時間にバスがあったはず」という感覚でバス停へ向かうこともあります。その結果、タイミングによってはバス停で次の便を長く待つことがあります。

**→ 本当に解決したい課題：**

月に数回利用する「いつもの移動」について、場所や行き方はなんとなく覚えていても、バス停名・路線名・時刻までは覚えていません。

そのため、本来であれば利用するたびにバス停名を調べたり、検索欄に入力したり、バス会社のWebサイトから時刻表を探したりする必要があります。しかし、その操作自体を面倒に感じ、「このくらいの時間にバスがあったはず」という感覚でバス停へ向かうこともあります。

その結果、タイミングによってはバス停で次の便を長く待つことになります。

毎回同じ移動について検索・入力を繰り返すのではなく、一度登録した自分の「いつもの移動」については、必要なときにすぐ次の便を確認できるようにし、「調べるのが面倒だから確認しない」という状態をなくしたいです。

## 4. 想定ユーザー

### 4-1. 想定しているユーザー

#### 年齢設定

- 年齢：特定の年代に限定しない
- 理由：このサービスで解決したい課題は年齢によって生じるものではなく、「月に数回程度、同じバスを利用する」という利用頻度によって生じると考えているためです。年齢を問わず、毎日利用するわけではないためバス停名や路線名、時刻までは覚えていない人を対象とします。

#### 生活・状況設定

- 生活・状況：普段は徒歩・自転車・車など別の交通手段を利用しており、駅へ向かうときなどに月に数回、同じ場所から同じ方面のバスを利用する人。
- 理由：利用するバス停の場所や目的地までの行き方はなんとなく覚えていても、利用頻度が低いため、バス停の正式名称・路線名・時刻までは覚えていません。そのため、バスを利用するたびに同じ情報を調べ直す必要があります。普段利用する移動をあらかじめ登録しておくことで、次回以降はアプリを開くだけで必要な情報を確認できるようにします。

#### 環境設定

- 環境：外出前や移動中に、スマートフォンからバスの時刻を確認する場面。
- 理由：外出前に知りたいのは、「いつもの場所から次のバスが何時に来るか」という情報です。バス会社のWebサイトを開き、バス停や方面を探して一日分の時刻表から次の便を探すのではなく、スマートフォンでNorutokiを開くことで、現在時刻から利用できる次の便をすぐに確認できるようにします。

### 4-2. 自分とユーザーの距離

- 自分自身

このサービスの想定ユーザーは、自分自身に近いです。私は普段バスを毎日利用するわけではなく、月に数回程度、同じ場所から同じ方面のバスを利用しています。利用するバス停の場所や目的地までの行き方はなんとなく覚えていますが、利用頻度が低いため、バス停の正式名称や路線名、時刻までは覚えていません。

そのため、バスを利用するたびにバス停名を調べたり、バス会社のWebサイトから時刻表を探したりしています。また、行きのバスだけでなく、外出先から帰る際にも「帰りのバスは次に何時に来るのか」を改めて調べることがあります。「前にも同じバスを調べたのに、また同じことを調べている」と感じることがあり、行きも帰りも含めて、この繰り返しをもっと簡単にできないかと考えたことがNorutokiの出発点です。

自分自身が実際に感じている不便をもとにしているため、まずは自分が日常生活の中で使いたいと思えるサービスを作り、実際に利用しながら改善していきたいと考えています。

### 4-3. 実際に使われる可能性について（需要・存在確認）

#### まず最初に使ってくれそうな人は誰か？

まずは、自分自身と同じように、毎日ではなく月に数回程度、同じバス停・同じ方面のバスを利用する人を想定しています。

普段は徒歩・自転車・車など別の交通手段を利用しているため、バス停の場所や目的地までの行き方はなんとなく分かっていても、バス停名や路線名、時刻までは覚えていない人です。

まずは自分自身で実際に利用し、その後、家族や知人など同じような利用状況の人にも使ってもらい、フィードバックを得たいと考えています。

#### その人は、どんな場面でこのアプリを思い出すか？

「そろそろ家を出よう」「駅までバスで行こう」と思ったときや、外出先から「そろそろ帰ろう」と思ったときです。

その際に「次のバスは何時だろう？」と思ったらNorutokiを開き、あらかじめ登録してある行き・帰りの交通情報から、現在時刻以降の次の便を確認します。

#### 今の生活の中で、代わりに使っているものは何か？

バスの時刻をきちんと確認するときは、Googleなどの検索エンジンやバス会社のWebサイトを利用しています。

一方で、毎回バス停名を調べて時刻表を確認すること自体を面倒に感じることもあり、「このくらいの時間にバスがあったはず」という過去の記憶や感覚を頼りに、そのままバス停へ向かうこともあります。

そのため、現在の代替手段は既存のWebサービスだけではなく、「調べずに感覚で向かう」という行動にもなっています。

#### それを置き換えてまで使う理由はあるか？

Googleマップやバス会社のWebサイトは、初めて行く場所への経路や詳しい交通情報を調べる場合には便利です。

一方、Norutokiが対象とするのは、「行き方はなんとなく分かっていて、月に数回繰り返し利用する移動」です。

最初に普段利用する行き・帰りのルートを登録しておけば、自分が利用するルートだけをまとめた「自分専用の交通情報」として利用できます。

次回からはバス停名を思い出したり、検索欄に入力したり、バス会社のWebサイトから該当する時刻表を探したりする必要はありません。

Norutokiを開けば、登録しているいつものルートから「次のバスが何時か」「あと何分で来るか」をすぐ確認できます。

新しい経路を検索しやすくするのではなく、一度登録した「いつもの移動では、もう検索や入力をしなくていい」という体験が、Norutokiを利用する理由になると考えています。

### 4-4. 導入・継続の流れ

#### 使い始めるまでに必要な行動

初回利用時に、自分が普段利用する「いつもの移動」を登録します。

例えば「家の近く → 駅」「駅 → 家」のように、繰り返し利用する行き・帰りのルートを登録し、それぞれのバス停や方面など、次の便を表示するために必要な情報を設定します。

最初の登録には一定の手間がかかりますが、一度登録すれば、次回以降は同じバス停名や路線名を調べたり、検索欄に入力したりする必要がありません。

そのため、「最初の1回だけ登録することで、その後何度も発生する検索や入力を減らす」という考え方で、導入時の負担よりも継続して利用するメリットが大きくなることを目指します。

#### 使い続けてもらうための流れ

ユーザーがバスを利用したいと思ったときにNorutokiを開くと、登録した自分専用の「いつもの移動」が表示されます。

利用したいルートを選択すると、現在時刻をもとに「次のバスが何時に来るか」「あと何分で来るか」をすぐ確認できます。

また、外出先から帰る際にも、あらかじめ登録している帰りのルートから次の便を確認できます。

毎回検索するのではなく、

「バスに乗ろうと思う」→「Norutokiを開く」→「いつものルートを選ぶ」→「次の便を確認する」

という少ない操作で利用できるようにすることで、継続して使いやすいサービスを目指します。

#### 継続して利用する理由

Norutokiは、毎日利用するサービスではなく、ユーザーがバスを利用するタイミングで思い出して使ってもらうサービスを想定しています。

月に数回の利用であっても、一度登録した「いつもの移動」が残っていることで、次にバスを利用するときには一から調べ直す必要がありません。

利用するたびに検索・入力する手間を減らし、「次のバスを知りたいときはNorutokiを開けばすぐ分かる」という状態を作ることが、継続利用につながると考えています。

## 5. 競合サービスとの比較

### 5-1. 競合サービス

Norutokiと近い目的で利用されるサービスとして、以下を想定しています。

- Googleマップ
- Yahoo!乗換案内
- バス会社が提供するWebサイト・時刻表

### 5-2. 競合サービスでできること

#### Googleマップ

Googleマップでは、出発地と目的地を指定して公共交通機関を利用した経路を検索できます。

また、よく利用する公共交通機関のルートを保存し、保存したルートから経路情報へアクセスする機能も提供されています。

そのため、「よく利用するルートを登録して後から確認する」という機能だけでは、Norutoki独自の価値にはならないと考えています。

#### Yahoo!乗換案内

Yahoo!乗換案内では、出発地・目的地・日時などを指定した乗換検索や、鉄道・バスの時刻表を確認できます。

バス時刻表についても、バス停名や曜日・日時を指定して調べることができます。

初めて利用する場所への経路検索や、さまざまな交通手段を含めた移動を調べる場合に便利なサービスです。

#### バス会社のWebサイト・時刻表

バス会社のWebサイトでは、各バス停や路線について詳しい時刻表を確認できます。

正確な情報を確認するためには便利ですが、自分の場合はバス停の正式名称や路線名を覚えていないことがあり、利用するたびに該当するバス停や方面を探す必要があります。

また、一日分の時刻表から現在時刻以降の便を自分で探す場合もあります。

### 5-3. Norutokiとの違い

Norutokiは、初めて行く場所への経路を検索することを主な目的とせず、「月に数回利用する、すでに行き方をなんとなく知っている移動」に特化します。

最初に普段利用する行き・帰りの移動を登録しておくことで、その後はバス停名や路線名を思い出して入力したり、経路を検索したり、時刻表から次の便を探したりする必要をなくします。

アプリを開くと、自分が登録した「いつもの移動」が表示され、現在時刻をもとに「次のバスが何時か」「あと何分で来るか」をすぐ確認できる体験を目指します。

Googleマップにも公共交通機関のルートを保存する機能がありますが、Norutokiでは「保存した経路を確認すること」ではなく、「いつもの移動について次に利用できる便をできるだけ少ない操作ですぐ確認すること」を中心に設計します。

### 5-4. 差別化を機能ではなく体験価値で表現する

既存の乗換案内サービスは、「どのように目的地まで行くか」を調べたい場面で非常に便利です。

一方、Norutokiが解決したいのは、「行き方はなんとなく分かっているので検索したくない。しかし、次のバスの時刻までは覚えていない」という場面です。

Norutokiが提供したい体験は、

「どのバスに乗ればいいか検索する」

のではなく、

「Norutokiを開けば、自分のいつもの移動について次のバスがすぐ分かる」

というものです。

検索や入力を便利にするのではなく、「いつもの移動では、そもそも検索や入力をしなくていい」状態を作ることをNorutokiの体験価値とします。

## 6. このサービスを使うことで生まれる価値

### 6-1. 利用前の状態

月に数回バスを利用するとき、バス停の場所や目的地までの行き方はなんとなく分かっていても、バス停名・路線名・時刻までは覚えていません。

そのため、バスに乗るたびにバス停名を調べたり、検索欄に入力したり、バス会社のWebサイトから時刻表を探したりする必要があります。

また、その操作自体を面倒に感じ、「このくらいの時間にバスがあったはず」という感覚でバス停へ向かうこともあります。

その結果、タイミングによっては次のバスまで長く待つことになります。

帰りについても同様で、外出先で「次の帰りのバスは何時だろう」と思ったときに、再び時刻表を調べる必要があります。

### 6-2. Norutokiを利用した後の状態

初回に普段利用する行き・帰りの「いつもの移動」を登録しておきます。

次回からはNorutokiを開くことで、自分が登録したいつもの移動から「次のバスが何時か」「あと何分で来るか」をすぐ確認できます。

これにより、バスを利用するたびにバス停名や路線名を思い出したり、検索欄に入力したり、一日分の時刻表から次の便を探したりする必要がなくなります。

外出前には次のバスを確認してから家を出ることができ、外出先でも帰りのバスをすぐ確認できるため、「調べるのが面倒だから、とりあえずバス停へ向かう」という行動を減らすことができます。

### 6-3. Norutokiが提供する価値

Norutokiが提供する価値は、単にバスの時刻表を表示することではありません。

「行き方はなんとなく分かっているが、バス停名や時刻までは覚えていない」という月に数回のいつもの移動について、毎回検索・入力する必要をなくすことです。

一度登録した自分専用の「いつもの移動」であれば、Norutokiを開くだけで次に利用できる便を確認できる状態を目指します。

これによって、

「次のバスを調べる」から「Norutokiを開けば分かる」

という行動の変化を生み出します。

### 6-4. 一言で表す提供価値

「いつもの移動を、検索しない。」

毎日利用するほどではないから時刻までは覚えていない。しかし、何度も利用しているから毎回検索するほどでもない。

Norutokiは、そんな「たまに使う、いつもの移動」を登録しておくことで、必要なときに次の便をすぐ確認できる、自分専用の交通情報アプリを目指します。

## 7. MVPと本リリース

### 7-1. MVPで実装する機能

MVPでは、「いつもの移動を一度登録しておけば、次回から検索や入力をせず、現在時刻から次に利用できる便をすぐ確認できる」というNorutokiの中心的な価値を検証します。

#### ユーザー登録・ログイン機能

ユーザーごとに自分専用の「いつもの移動」を保存できるようにします。

- ユーザー登録
- ログイン・ログアウト

#### いつもの移動の登録・管理機能

普段利用する移動を登録できるようにします。

例えば、

- 家の近く → 駅
- 駅 → 家

など、自分が繰り返し利用する移動を登録します。

登録した移動については、一覧表示・編集・削除ができるようにします。

#### バス時刻の登録・管理機能

登録した「いつもの移動」に対して、次の便を判定するために必要な時刻表データを登録・管理できるようにします。

MVPでは、まず時刻表を登録して次の便を判定できる仕組みの完成を優先し、実現可能な方法で時刻表データを登録できるようにします。

公共交通データ・APIの利用や画像からの読み取りについては技術検証を行い、実装難易度を確認したうえで、本リリース以降の登録方法として検討します。

平日・土曜日・休日など、曜日によって異なる時刻表についても、MVPの実装範囲と合わせて対応方法を検討します。

#### 次のバス表示機能

現在時刻と登録された時刻表を比較し、現在時刻以降で最も近い便を表示します。

例えば、

「次のバス 18:42」「あと7分」

のように、ユーザーが時刻表全体を見ることなく、次に利用できる便をすぐ確認できるようにします。

次の1便だけでなく、その後の2〜3便も確認できるようにし、「今出るか、次のバスにするか」を判断できるようにします。

#### 行き・帰りのルート表示

「家の近く → 駅」「駅 → 家」のように、行きと帰りの移動をそれぞれ登録し、自分専用のいつもの移動として一覧からすぐ確認できるようにします。

これにより、外出前だけでなく、外出先から帰る際にも次のバスをすぐ確認できるようにします。

### 7-2. MVPで検証したいこと

MVPでは、機能の多さではなく、Norutokiの中心的な体験に価値があるかを検証します。

具体的には、

- バスに乗る際の検索・入力回数が減るか
- 「調べるのが面倒だから感覚でバス停へ向かう」という行動が減るか
- Norutokiを開いてから短時間で次のバスを確認できるか
- 月に数回の利用でも、次にバスへ乗るときにNorutokiを思い出して使うか
- 一度「いつもの移動」を登録する手間に対して、その後の便利さを感じられるか

を確認します。

まずは自分自身で実際の移動時に利用し、その後、同じように月に数回バスを利用する人にも使ってもらい、フィードバックを得ながら改善します。

### 7-3. 本リリースで追加したい機能

MVPでNorutokiの中心的な価値を検証した後、より便利に利用できるように機能を追加します。

#### 初回登録を簡単にする機能

Norutokiは「検索や入力の手間を減らす」ことを目的としているため、初回登録自体が大きな負担にならないように改善します。

バス停や路線、時刻表などをできるだけ簡単に登録できる方法を検討します。

#### 現在地を利用した表示

位置情報を利用し、現在地に応じて「行き」「帰り」など利用する可能性が高いルートを優先して表示する機能を検討します。

#### バス停までの移動時間を考慮した表示

ユーザーがいる場所からバス停までの徒歩時間などを考慮し、「このバスに乗るなら○分後までに出発する」といった情報を表示できるようにすることを検討します。

#### お気に入り・並び替え

複数の「いつもの移動」を登録した場合に、よく利用するルートを上部に表示したり、自分の使いやすい順番に並べ替えたりできるようにします。

#### 通知機能

登録したバスの出発時刻が近づいた際に通知する機能を検討します。

#### 地元ならではのおすすめルート共有機能

地域のユーザーが、実際に利用しているおすすめの移動方法や、地元だからこそ知っている交通情報を投稿・共有できる機能を追加します。

例えば、「このバス停から乗った方が便利」「この時間帯はこちらのルートがおすすめ」「この施設へ行くならこちらの停留所から歩いた方が近い」など、一般的な経路検索だけでは分かりにくい地域ならではの情報を共有できるようにします。

また、投稿されたおすすめルートを見たユーザーが、そのルートを自分の「いつもの移動」として登録できる仕組みについても検討します。

これにより、「地元の人が知っている便利な移動を見つける」だけでなく、「見つけた移動を自分のいつもの移動として登録し、次回から検索せず利用する」というNorutokiの中心的な体験につなげます。

### 7-4. MVPでは実装しないこと

Norutokiは乗換案内サービスそのものを作ることが目的ではないため、MVPでは以下のような機能は実装しません。

- 全国のあらゆる場所への経路検索
- 電車・バスを組み合わせた高度な乗換検索
- 運賃の比較
- 最短経路・最安経路の検索
- リアルタイムのバス位置情報
- 運行遅延情報
- AIによる経路提案

これらの機能ではなく、「登録したいつもの移動について、検索や入力をせず次の便をすぐ確認できる」という体験の実現をMVPでは優先します。

## 8. 懸念点とその対応

### 8-1. 時刻表データをどのように取得するか

Norutokiの中心機能である「現在時刻から次に利用できるバスを表示する」ためには、バスの時刻表データが必要です。

理想としては、ユーザーが利用するバス停や方面を選択するだけで時刻表を取得できる状態ですが、すべてのバス会社が同じ形式でデータやAPIを公開しているとは限りません。

そのため、利用できる公共交通データやAPIについて調査し、MVPでどこまで自動化できるかを検討します。

自動取得が難しい場合は、MVPでは対象とする交通機関や地域を限定する、または必要最低限の情報をユーザーが登録する方法も検討します。

### 8-2. 初回登録が面倒にならないか

Norutokiは「毎回検索・入力する手間を減らす」ことを目的としたサービスです。

そのため、最初に「いつもの移動」を登録する際に、バス停名・路線名・一日分の時刻表などを大量に入力する必要があると、サービスのコンセプトと矛盾してしまいます。

初回登録については、できるだけ少ない操作で完了できることを目指します。

MVPでは実装難易度とのバランスを考えながら登録方法を決定し、実際に利用して「最初の登録の手間より、その後検索しなくてよくなる便利さの方が大きい」と感じられるかを検証します。

### 8-3. ダイヤ改正への対応

バスの時刻表は、ダイヤ改正によって変更される可能性があります。

登録した時刻表が古いまま表示されると、ユーザーが実際のバスに乗れない可能性があり、サービスへの信頼性を大きく損ないます。

外部の交通データから時刻表を取得する場合は、データの更新方法や更新頻度を調査します。

ユーザー自身が時刻表を登録する方式の場合は、登録内容を簡単に編集できるようにするなど、ダイヤ改正後に更新しやすい仕組みを検討します。

### 8-4. 曜日や祝日による時刻表の違い

バスの時刻表には、平日・土曜日・日曜日・祝日などによって異なるダイヤが設定されている場合があります。

単純に現在時刻だけで次の便を判定すると、実際には運行していない便を表示してしまう可能性があります。

そのため、現在の日付と曜日を判定し、その日に対応した時刻表から次の便を表示できる仕組みを検討します。

祝日についても、MVPでどこまで対応するかを実装難易度と合わせて判断します。

### 8-5. バスの遅延や運休には対応できない可能性がある

時刻表上の出発時刻と、実際にバスが到着する時刻が一致するとは限りません。

交通状況による遅延や運休など、リアルタイムの運行状況を取得するには、バス会社などが提供するリアルタイムデータが必要になる可能性があります。

NorutokiのMVPでは、まず「時刻表上で次に利用できる便をすぐ確認すること」を中心に開発し、リアルタイムの遅延・運休情報については対象外とします。

将来的に利用可能なデータやAPIがある場合は、リアルタイム情報との連携も検討します。

### 8-6. 既存サービスとの差別化が十分か

GoogleマップやYahoo!乗換案内など、公共交通機関を検索できる既存サービスはすでに存在しています。

また、既存サービスにもルート保存やお気に入りなどの機能があるため、単に「よく使うルートを登録できる」だけでは十分な差別化にならない可能性があります。

Norutokiでは機能の多さで競うのではなく、

「月に数回利用する、行き方はなんとなく分かっている移動」

に対象を絞ります。

そして、

「検索する → 条件を入力する → 経路を確認する」

のではなく、

「Norutokiを開く → 自分のいつもの移動を見る → 次の便が分かる」

という、次の便を確認するまでの操作をできるだけ少なくする体験によって差別化を図ります。

MVP公開後は、実際にユーザーに使ってもらい、この体験に既存サービスから使い分けるだけの価値があるかを検証します。

### 8-7. 月に数回の利用でも継続して使ってもらえるか

Norutokiの想定ユーザーは、毎日ではなく月に数回程度バスを利用する人です。

そのため、一般的なサービスと比べるとアプリを開く頻度は低くなる可能性があります。

一方でNorutokiでは、毎日利用してもらうことではなく、「バスを利用するタイミングではNorutokiを思い出してもらうこと」を継続利用と考えます。

一度登録した自分の「いつもの移動」が残っていることで、次回バスを利用するときにも一から検索する必要がない状態を作り、月に数回であっても繰り返し利用されるかを検証します。

### 8-8. 初回登録を写真から行えるか

Norutokiでは、初回登録時の入力負担を減らすため、バス停に掲示されている時刻表をスマートフォンで撮影し、画像から時刻を読み取って登録する機能を検討します。

画像認識やOCRを利用することで、一日分の時刻をすべて手入力するのではなく、撮影した時刻表から平日・土曜日・休日などの時刻を自動的に抽出することを目指します。

ただし、バス会社によって時刻表のレイアウトが異なることや、写真の角度・明るさ・文字サイズなどによって正しく読み取れない可能性があります。

そのため、読み取った内容をそのまま登録するのではなく、ユーザーが解析結果を確認・修正してから登録する仕組みを検討します。

MVPに含めるかについては、画像認識・OCRの技術検証を行い、実装難易度を確認したうえで判断します。

## 9. 今後の発展

Norutokiでは、まず「いつもの移動について、検索や入力をせず次の便をすぐ確認できる」という体験の実現を優先します。

MVPでこの価値を検証したうえで、ユーザーがより少ない操作で利用できるよう、以下のような機能への発展を検討します。

### 9-1. 写真からの時刻表登録

バス停に掲示されている時刻表をスマートフォンで撮影し、画像認識・OCRを利用して時刻表を読み取る機能を検討します。

例えば、写真から

- 平日
- 土曜日
- 日曜日・祝日
- 各時間帯の出発時刻

などを読み取り、Norutokiの時刻表データとして登録します。

読み取り結果をそのまま登録するのではなく、ユーザーが内容を確認・修正してから保存できるようにすることで、誤認識にも対応できる仕組みを目指します。

これにより、一日分の時刻を手入力する必要をなくし、「最初に一度撮影するだけで、その後は検索しなくてよい」という体験につなげます。

### 9-2. 公共交通データとの連携

利用可能な公共交通データやAPIがある場合は、バス停・路線・時刻表などの情報を自動的に取得する機能を検討します。

ユーザーが一から時刻表を登録するのではなく、利用するバス停や方面などを選択することで「いつもの移動」を登録できる状態を目指します。

また、データを自動取得できるようになれば、ダイヤ改正時の時刻表更新についてもユーザー自身の負担を減らせる可能性があります。

### 9-3. 現在地に応じた「いつもの移動」の表示

位置情報を利用し、現在地に応じて利用する可能性が高い「いつもの移動」を優先して表示する機能を検討します。

例えば、自宅付近にいる場合は、

「家の近く → 駅」

を優先して表示し、外出先の駅付近にいる場合は、

「駅 → 家」

を優先して表示します。

これにより、ユーザーが行き・帰りのルートを毎回選択する操作も減らし、アプリを開いてから次の便を確認するまでの操作をさらに少なくすることを目指します。

### 9-4. バス停までの移動時間を考慮した表示

現在地からバス停までの徒歩時間などを考慮し、単に「次のバスがあと何分で来るか」だけではなく、「そのバスに乗るためにはあと何分以内に出発すればよいか」を表示する機能を検討します。

例えば、

「次のバス 18:42」「あと12分」「バス停まで徒歩5分」「あと7分以内に出発」

といった情報を表示します。

これにより、ユーザーが時刻を確認した後に自分で逆算する必要を減らし、「いつ家を出ればよいか」までNorutokiだけで判断できる状態を目指します。

### 9-5. 通知機能

ユーザーが利用したい便について、出発準備を始める時間や家を出る時間が近づいた際に通知する機能を検討します。

例えば、「18:42のバスに乗るため、あと5分で家を出る」といった通知を行います。

これにより、アプリを何度も開いて時刻を確認する必要をさらに減らすことができます。

### 9-6. リアルタイム運行情報との連携

利用可能なリアルタイム交通データがある場合は、バスの遅延・運休・現在位置などの情報との連携を検討します。

時刻表上では「あと5分」となっていても、実際には遅延している場合があります。

将来的には、時刻表上の情報だけではなく実際の運行状況も確認できるようにすることで、より実用的な交通情報を提供できる可能性があります。

### 9-7. バス以外の「いつもの移動」への拡張

まずは、自分自身が実際に感じている課題であるバス利用を中心に開発します。

その後、同じように「行き方は分かっているが、時刻だけ確認したい」という場面があれば、電車や送迎バスなど、他の交通手段への対応も検討します。

ただし、一般的な乗換案内サービスのようにあらゆる経路を検索できるサービスを目指すのではなく、あくまで「自分が繰り返し利用する、いつもの移動をすぐ確認する」というNorutokiの中心的な価値を維持したまま発展させます。

### 9-8. 発展後も変えないNorutokiの考え方

機能を追加していく場合でも、Norutokiでは機能の多さより「次の便を確認するまでの手間を減らすこと」を優先します。

「検索する」「入力する」「時刻表から探す」「時間を自分で計算する」

といった、いつもの移動で繰り返している小さな操作を一つずつ減らし、

「バスに乗ろうと思う」→「Norutokiを開く」→「いつ出ればよいか分かる」

という体験に近づけていくことを、今後の発展の方向性とします。

## 10. 技術スタック・技術選定

### 10-1. 使用予定の技術

#### バックエンド

- Ruby
- Ruby on Rails

RUNTEQで学習しているRuby on Railsを使用します。

Norutokiでは、ユーザー情報、「いつもの移動」、時刻表など複数のデータを関連付けて管理する必要があります。

また、現在時刻と登録された時刻表を比較して次に利用できる便を判定するなど、サーバー側での処理も必要になるため、Railsを中心にアプリケーションを構築します。

#### フロントエンド

- HTML
- CSS
- JavaScript

MVPでは、フロントエンドにReactなどの別フレームワークを導入せず、Railsを中心とした構成で開発する予定です。

Norutokiはスマートフォンから短時間で利用することを想定しているため、レスポンシブ対応を行い、「アプリを開いてから次の便を確認するまで」の操作をできるだけ少なくしたUIを目指します。

必要に応じてJavaScriptを使用し、画面上の操作性を改善します。

#### データベース

- PostgreSQL

ユーザー、「いつもの移動」、時刻表、曜日ごとの運行情報などを保存・関連付けるために使用します。

例えば、

User ↓いつもの移動（Route）↓時刻表（Timetable）↓出発時刻（Departure）

のように、必要なデータを関連付けて管理することを想定しています。

実際のテーブル設計については、ER図を作成したうえで決定します。

#### 開発環境

- Docker
- Docker Compose
- Git
- GitHub

開発環境はDockerを利用して構築し、Git・GitHubでソースコードを管理します。

GitHubでは機能ごとにブランチを作成し、Pull Request単位で開発を進めます。

### 10-2. 現在時刻から次の便を判定する仕組み

Norutokiの中心機能として、現在の日付・時刻と登録された時刻表を比較し、現在時刻以降で最も近い便を取得します。

例えば現在時刻が18:35で、

18:20 18:42 19:05 19:30

という時刻表が登録されている場合、

「次のバス 18:42」「あと7分」

と表示します。

また、その後の2〜3便についても取得し、ユーザーが「次の便に乗るか、その次の便にするか」を判断できるようにします。

曜日によって時刻表が異なる場合は、現在の日付から平日・土曜日・休日などを判定し、その日に対応した時刻表を利用する仕組みを検討します。

### 10-3. 外部データ・APIの利用

バス停や路線、時刻表などの登録負担を減らすため、利用可能な公共交通データやAPIについて調査します。

候補として、GTFS・GTFS-JPなどの公共交通データの利用可能性を調査します。

ただし、交通事業者によってデータの公開状況が異なる可能性があるため、「全国すべてのバス情報を取得すること」をMVPの前提にはしません。

利用可能なデータ、実装難易度、利用条件などを確認し、MVPで現実的に利用できる方法を決定します。

### 10-4. 画像認識・OCRの利用

初回登録の負担を減らす方法として、バス停に掲示されている時刻表をスマートフォンで撮影し、画像から時刻を読み取る機能を検討します。

技術的には、

「時刻表を撮影」↓「画像から文字を読み取る」↓「時刻データとして整形する」↓「ユーザーが確認・修正する」↓「データベースへ登録する」

という流れを想定しています。

OCRについては、自前ですべての画像認識処理を実装するのではなく、利用可能なOCRサービスやライブラリなどを調査します。

ただし、時刻表のレイアウトはバス会社によって異なり、画像の角度や明るさなどによって認識精度が変わる可能性があります。

そのため、MVPに含めるかどうかは事前に技術検証を行ったうえで判断し、実装する場合も読み取った結果をユーザーが確認・修正してから登録する設計を検討します。

### 10-5. 本リリース以降で利用を検討する技術

MVP完成後、必要に応じて以下の技術・外部サービスの利用を検討します。

- 位置情報を取得するためのGeolocation API
- 現在地からバス停までの距離・移動時間を取得するための地図・経路関連API
- バスのリアルタイム運行情報
- 通知機能
- OCR・画像認識
- 公共交通データとの連携

これらを最初からすべて導入するのではなく、MVPでNorutokiの中心的な価値を検証した後、必要性の高いものから追加します。

### 10-6. 技術選定で重視すること

Norutokiでは、新しい技術を多く使用することよりも、まずサービスの中心となる体験を完成させることを優先します。

MVPで最も重要なのは、

「いつもの移動を登録する」↓「Norutokiを開く」↓「現在時刻から次に利用できる便が分かる」

という一連の流れです。

そのため、RUNTEQで学習しているRuby on Railsを中心に開発し、Reactなど追加の学習コストが大きい技術については、MVPでは必要性が明確でない限り導入しません。

一方、公共交通データ・OCR・位置情報など、Norutokiの利用体験を大きく改善できる技術については、事前に小さな技術検証を行い、実現可能性を確認してから導入を判断します。

### 10-7. キャッチアップが必要な技術とリスク

現時点で特に技術調査・キャッチアップが必要になる可能性が高いものは、以下です。

- GTFS・GTFS-JPなどの公共交通データの扱い
- 外部APIとの連携
- 画像認識・OCR
- 日付・曜日・祝日を考慮した時刻表の判定
- 位置情報の取得
- 本リリースでの通知機能

これらをすべてMVPの必須要件にすると開発期間が長くなる可能性があります。

そのため、まずRailsでNorutokiのコア機能を完成させることを優先し、新しい技術については「その技術がなければNorutokiの価値を検証できないか」を基準にMVPへ含めるかを判断します。

技術的に難しい機能については、対象範囲を限定する、より簡単な方法へ変更する、本リリース以降へ移すなど、卒業制作として完成させることを優先して調整します。
